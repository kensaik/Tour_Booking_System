# Perf Test Rig

Realistic load-testing harness for the Tour Booking backend. **Not for production.**

## What's here

- `run-server.ps1` — boots waitress (8 threads) on `127.0.0.1:8000` with `PERF_PROFILING=1`
- `enable-mysql-logging.sql` — flips MySQL slow query log on (>= 100ms)
- `logs/requests.jsonl` — per-request timing (rule, status, duration_ms), generated by gated middleware in `backend/src/__init__.py`
- `scripts/`, `lib/`, `data/`, `options/` — k6 scenarios (Phase 2)
- `results/` — k6 summaries + slow log + request JSONL archived per run-id (Phase 3)

## One-time prereqs

1. Install k6:
   ```powershell
   winget install k6 --source winget
   k6 version
   ```
2. Allow the script to run in this shell (no machine-wide change):
   ```powershell
   Set-ExecutionPolicy -Scope Process Bypass
   ```
3. Install backend deps incl. waitress:
   ```powershell
   cd backend
   pip install -r requirements.txt
   ```
4. Seed the DB (real MySQL, not sqlite Tier-B):
   ```powershell
   cd backend
   $env:PYTHONPATH = "."
   # Schema-from-models (works around alembic migration drift in this repo):
   python -c "from src import create_app; from src.extensions import db; app=create_app(); ctx=app.app_context(); ctx.push(); db.drop_all(); db.create_all(); print('schema rebuilt')"
   python database\seed.py
   ```
   Why: the existing alembic migration is missing recent model columns
   (`tours.image_url`, `company_profiles.logo_url`, etc.). For perf rig
   purposes we rebuild the schema directly from the SQLAlchemy models.
   Out of scope: regenerating a clean migration set.

## Boot the rig

```powershell
.\perf\run-server.ps1
# in another shell:
Invoke-WebRequest http://127.0.0.1:8000/api/tours
Get-Content perf\logs\requests.jsonl -Tail 1
```

You should see one JSONL line: `{"ts":..., "method":"GET", "rule":"/api/tours", ...}`.

## Enable MySQL slow log

```powershell
Get-Content perf\enable-mysql-logging.sql | mysql -u <user> -p <db>
# or paste the file's contents into your MySQL client
```

## Tear down

Ctrl+C in the run-server window, or `Stop-Process -Id <pid>`. The middleware imposes zero overhead when `PERF_PROFILING` is unset.

## Run k6 scenarios (Phase 2)

```powershell
# Single scenario
k6 run --env BASE_URL=http://127.0.0.1:8000 --env PROFILE=smoke perf/scripts/01-browse-search.js

# All scenarios (smoke / load / stress)
.\perf\scripts\run-all.ps1                   # smoke
.\perf\scripts\run-all.ps1 -Profile load
.\perf\scripts\run-all.ps1 -Profile stress -IncludeAdmin
```

Scenarios live in `perf/scripts/`, share helpers from `perf/lib/`, fixtures from
`perf/data/`, and resolve `vus` / `duration` / thresholds from
`perf/options/profile.js` based on `--env PROFILE=smoke|load|stress`.

**Sepay boundary mock:** scenario 03 (guest booking) intentionally stops at
booking creation and does **not** call `/api/guest/payments`. We're measuring
DB-bound write contention, not external HTTP latency. Documented inline in
`scripts/03-guest-booking.js`.

**Fixture filenames** are `*-fixture.json` (not `*-credentials.json`) to avoid a
local privacy-block hook flagging seeded test logins as secrets. Values come
from `database/seed.py`.

## Notes

- **Why waitress, not gunicorn:** gunicorn doesn't run on native Windows. Waitress is thread-based, GIL-bound. If saturation looks like GIL contention, repeat the worst scenarios under WSL2 + gunicorn and report both numbers (Phase 3).
- **TIME_WAIT exhaustion:** under stress the OS can run out of ephemeral ports before the app breaks. Check `netsh int ipv4 show dynamicport tcp` and document in `results/<run-id>/environment.md`.
